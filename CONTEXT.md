## Decisões de arquitetura
- Cadastro de peça simplificado em 2026-09-26 (decisão revista) — Felipe (cliente) definiu que não haverá diferenciação de campos técnicos por tipo de pedra. A decisão anterior (registrada aqui até 2026-09-26) era usar `Product.attributes` (Json) para quilate, corte, origem, certificado/laudo gemológico, cor, claridade etc., com schema leve descrito por `Category.attributeSchema`. Todo esse sistema (model `Category`, `Product.categoryId`/`category`/`attributes`, rotas `/api/categories`, `DynamicAttributeFields.tsx`) foi **removido por completo** — migration `20260926130000_remove_category_and_attributes` dropa a tabela `Category` e as colunas `categoryId`/`attributes` de `Product` (produtos existentes perdem essa informação, aceito e confirmado antes de aplicar). Cadastro de peça hoje é só: nome, descrição, preço, SKU, peso (`weightGrams`), tamanho (`sizeCm`), estoque opcional e fotos — campos fixos, iguais para qualquer peça
- Categorias/subcategorias reintroduzidas em 2026-09-26 (migration `20260926150000_add_categories`), mas só para organização/navegação/filtro do catálogo — sem trazer de volta `attributeSchema`/`attributes`. Models `Category` (id, name, slug) e `Subcategory` (id, name, slug, categoryId); `Product.categoryId` obrigatório, `Product.subcategoryId` opcional (null quando a categoria não tem subcategorias). Estrutura real fornecida pelo cliente: Pedras Brutas (Pedras Brutas Peça, Capelas de Ametista, Capelas de Citrino, Pedras Exclusivas), Pedras Polidas (Pedras Roladas, Pedras Polidas Exclusivas), Big (Ametistas, Calcitas, Citrinos), Formas, Homedecor e Acessorios (sem subcategorias) — populada via `prisma/seed.ts` (dados em `prisma/seedData.ts`). **"Formas" era subcategoria de Big e virou CATEGORIA de nível 1 em 2026-10-05** (ver seção "Formas virou categoria" abaixo). Rota `GET /api/categories` é pública (sem `requireAuth`), pensada para navegação/filtro do catálogo público; `GET /api/products` aceita filtro opcional por `categoryId`/`subcategoryId`. Validação de categoria/subcategoria obrigatória fica no handler das rotas de produto (`resolveSubcategoryId` em `product.routes.ts`), não no Zod, porque depende de consulta ao banco (se a categoria tem subcategorias)
- Peso (`weightGrams`, gramas) e tamanho (`sizeCm`, centímetros) — campos fixos do `Product` desde 2026-09-25, obrigatórios no cadastro (Decimal, `@default(0)` só como rede de segurança de migration)
- Estoque tipicamente unitário: `trackStock=false` (padrão, peça única sem controle de quantidade) ou `trackStock=true` + `stockQty=1` quando o admin preferir controlar disponibilidade explicitamente
- Painel admin invisível ao público, protegido por JWT (`requireAuth`), sem link público; frontend usa `ProtectedRoute`
- Upload de imagem via URL assinada do R2 — backend nunca recebe o arquivo (`presign` → `PUT` direto → confirma registro `ProductImage`)

## Frete nacional — Parte 1A implementada em 2026-10-03 (backend + admin; internacional é a Parte 1B, ainda não implementada)
Decisões de produto (já tomadas, não revisitar sem pedido explícito):
- Cliente não tem contrato com os Correios — frete nacional é cotação automática via Melhor Envio, usando **somente** o endpoint de cálculo (`shipment/calculate`, consulta sem custo). Nunca chamar carrinho/compra/geração ou cancelamento de etiqueta a partir deste projeto
- Dimensões de embalagem são estimadas automaticamente a partir de `sizeCm`/`weightGrams` da peça (caixa cúbica = `sizeCm + 2×SHIPPING_PADDING_CM` por lado, peso = `weightGrams + SHIPPING_PACKAGING_WEIGHT_G`), com `Product.packageLengthCm/packageWidthCm/packageHeightCm` opcionais para o admin corrigir quando a estimativa erraria (peça muito achatada/alongada etc.)
- Todo valor monetário no servidor é BRL, `number` com 2 casas, nunca string formatada — conversão para USD é só no frontend (reaproveita `GET /api/exchange-rate` já existente)
- País diferente de BR responde "indisponível" (`reason: "not_configured"`) nesta parte — frete internacional de verdade é a Parte 1B

Arquitetura (`backend/src/lib/shipping/`):
- `types.ts` define o contrato `ShippingProvider`/`ShippingQuoteResult` sem depender de env/prisma/fetch — um provider internacional (Parte 1B) implementa a mesma interface sem alterar o endpoint público
- `packageEstimator.ts` (função pura, testada) calcula a caixa; `limits.ts` guarda os mínimos (piso, aplicado no estimador) e máximos (teto, checado no provider antes de chamar a API) de dimensão/peso — **valores padrão Correios/transportadoras parceiras (16×11×2cm, 300g mínimo; 105cm maior lado, 200cm soma dos lados, 30kg máximo), não publicados pela API da Melhor Envio, ajustáveis se o cliente trocar de transportadora**
- `melhorEnvioProvider.ts` implementa `ShippingProvider` chamando só `POST /api/v2/me/shipment/calculate` (prod `https://melhorenvio.com.br`, sandbox `https://sandbox.melhorenvio.com.br`), payload `products[]` (um item por produto do carrinho, com `quantity` — a própria Melhor Envio decide o empacotamento), `insurance_value` = preço unitário real do produto. Timeout 8s via `AbortController`, no máximo 1 retry (só para erro de rede/timeout/5xx; erro de validação ou 401/403 não tenta de novo). Serviço individual com `error` ou preço inválido é omitido do resultado (campo `error` por item não é documentado oficialmente pela Melhor Envio, mas existe na prática — tratado defensivamente)
- `quoteService.ts` orquestra: cache (10min, chave país+CEP+itens) → busca produtos reais no banco (nunca confia em peso/preço/dimensão do cliente) → estima embalagem por item → chama o provider → combina com `viaCep.ts` (cidade/estado, nunca bloqueia a cotação se falhar)
- Rate limit simples por IP (`middleware/rateLimit.ts`, 20 req/min) em `POST /api/shipping/quote` — não havia infra de rate limit no projeto antes desta parte, foi implementada aqui

Contrato da API (consumido pelo frontend público na Parte 2 — carrinho/checkout):
- `POST /api/shipping/quote` — body `{ country: "BR", postalCode, items: [{ productId, quantity }] }` (país alpha-2; CEP aceita máscara, normalizado para 8 dígitos; quantidade 1-99). Resposta: `{ destination, mode: "domestic"|"international", options: [{ id, carrier, service, priceBRL, deliveryDaysMin, deliveryDaysMax, kind: "quoted"|"estimated" }], requiresConfirmation, notice: "taxes_not_included"|null, unavailable: null|{ reason } }`. `reason` ∈ `provider_error`, `no_rates_configured`, `invalid_destination`, `over_limits`, `incomplete_product_data`, `not_configured`. Nenhum texto pronto em nenhum idioma — o frontend traduz pelos códigos
- `GET /api/shipping/postal-code/:code` — `{ postalCode, city, state }` via ViaCEP; `city`/`state` vêm `null` (200, nunca erro) se o ViaCEP falhar
- `GET /api/shipping/status` (admin, `requireAuth`) — `{ domestic: { melhorEnvioTokenConfigured, originCepConfigured, sandbox }, international: null }`, nunca expõe valores, só booleanos. Página "Frete" no admin (`/admin/frete`) é só leitura nesta parte

Variáveis de ambiente (todas opcionais no boot — sem token/CEP de origem, a rota responde "indisponível" em vez de derrubar o servidor): `MELHOR_ENVIO_TOKEN`, `MELHOR_ENVIO_USER_AGENT` (formato `"Nome da aplicação (email técnico)"`, exigido pela Melhor Envio), `MELHOR_ENVIO_SANDBOX`, `SHIPPING_ORIGIN_CEP`, `SHIPPING_PACKAGING_WEIGHT_G` (default 200), `SHIPPING_PADDING_CM` (default 3). **Atenção: o token do Melhor Envio expira periodicamente e precisa ser renovado manualmente no painel deles (Gerenciar > Tokens) — não há renovação automática; quando expirar, o provider loga "token do Melhor Envio inválido ou expirado" e a rota passa a responder indisponível até o token ser trocado no ambiente do servidor.**

Campo de produto novo (admin): seção recolhível "Embalagem (opcional)" no formulário (`ProductForm.tsx`), 3 campos opcionais em cm — some do payload quando vazios (`null`), vão direto para `packageLengthCm/Width/Height` do `Product`.

### Frete nacional — interface do comprador (Parte 2) — 2026-10-05
- **Contrato real** (`routes/shipping.routes.ts`, `schemas/shipping.schema.ts`, `lib/shipping/types.ts`): `POST /api/shipping/quote` com `{ country: "XX", postalCode?, items: [{ productId, quantity 1–99 }] }` → `{ destination: { country, postalCode, city|null, state|null }, mode: "domestic"|"international", options: [{ id, carrier, service, priceBRL, deliveryDaysMin|null, deliveryDaysMax|null, kind: "quoted"|"estimated" }], requiresConfirmation, notice: "taxes_not_included"|null, unavailable: null|{ reason } }`. `reason` ∈ `provider_error`, `no_rates_configured`, `invalid_destination`, `over_limits`, `incomplete_product_data`, `not_configured`. Erros HTTP: 400 (CEP inválido; produto inexistente/inativo), **429** (limite de 20/min por IP, só em `/quote`), 5xx. `GET /api/shipping/postal-code/:code` (só Brasil, 8 dígitos) → `{ postalCode, city, state }` (nulos se o ViaCEP falhar; nunca erro).
- **Unidade do prazo:** `deliveryDaysMin/Max` vêm do campo `delivery_time`/`delivery_range` do Melhor Envio. A documentação do provedor não pôde ser consultada (domínio bloqueado no ambiente de desenvolvimento) e nada no repositório confirma se são dias úteis — por isso a tela escreve só **"dias"** (nunca "dias úteis"; há teste que impede). Confirmar na documentação antes de trocar o texto.
- **`postalCode` fora do Brasil (única mudança de backend desta parte):** o schema exigia `postalCode` não vazio para QUALQUER país, o que impedia a interface de tratar o código postal como opcional fora do Brasil. Passou a `z.string().optional().default("")`; o Brasil continua exigindo 8 dígitos (a rota já devolvia 400 para vazio/inválido). Observação: a rota normaliza removendo tudo que não é dígito (para países com código alfanumérico o `destination.postalCode` devolvido perde as letras) — a interface não depende desse eco e mostra o que o comprador digitou.
- **Tela:** bloco "Calcular frete" no carrinho (país com `Intl.DisplayNames`, 249 códigos ISO alpha-2, Brasil primeiro; CEP com máscara; cidade/UF pelo ViaCEP; botão sem chamada por tecla; recálculo automático só se o carrinho mudar depois de já haver cotação, debounce de 600 ms; respostas atrasadas descartadas; 429 desativa o botão por 15 s). Cartões de opção (radio nativo) com selos "Mais barato"/"Mais rápido" só com mais de uma opção e sem empate artificial; "Estimativa" quando `kind: "estimated"`. Cada `unavailable.reason` e cada falha (rede, timeout, 429, 400) tem mensagem humana e saída ("combinar pelo WhatsApp"). Resumo Subtotal/Frete/Total no carrinho e no checkout. O frete **nunca bloqueia o pedido**.
- **Valores:** centavos inteiros já arredondados; em inglês, mesma cotação do dia dos preços; total = soma das parcelas exibidas (`lib/shipping/money.ts`).
- **Persistência** (`localStorage` `cinzeleagema_shipping`, sempre em try/catch): país, CEP e escolha; a cotação só vale com a mesma assinatura do carrinho (ids+quantidades) e menos de 30 min; `CartProvider.clear()` limpa cotação e escolha (país/CEP ficam).
- **WhatsApp:** a mensagem inclui destino, serviço/preço/prazo ou "a combinar", e o total; estimado/internacional levam "a confirmar pelo atendimento" e (internacional) "Impostos de importação não incluídos". **O frete NÃO é enviado ao FluxioDesk**: `createOrderSchema` descarta campos extras e o contrato de pedidos não foi alterado (`totalEstimate` segue sendo o subtotal dos produtos) — quando o pedido é entregue pelo FluxioDesk o frete é combinado depois pelo atendimento. **Linha de cotação (só inglês):** quando a conversão para dólar foi aplicada, a última linha da mensagem (separada por uma linha em branco) é `Exchange rate used: US$ 1 = R$ 5.32 (rate of the day)` — mesma cotação que converteu os valores, 2 casas e ponto decimal, sem segunda consulta; sem conversão (cotação indisponível) ou em português, não há linha. `(approximate rate)` aparece quando a cotação é aproximada: `source` = `stale` ou `fallback`, OU mais de 24 h pelo `updatedAt` (resposta sem `source`, ex.: backend antigo, vale só a regra da idade; `isRateApproximate` em `lib/exchangeRateQuality.ts`). **`GET /api/exchange-rate`** devolve `{ rate, updatedAt, source }`, com `source` aditivo: `live` (consulta externa nas últimas 24 h, inclusive servida do cache nesse prazo), `stale` (a consulta falhou e o cache tem mais de 24 h; mantém o valor e o `updatedAt` antigos) ou `fallback` (valor de emergência 5,3). O fallback NÃO vale como fresco por 24 h: o backend tenta a API externa de novo depois de 5 minutos (`FALLBACK_RETRY_INTERVAL_MS`, nunca a cada requisição) e volta a `live` se a consulta funcionar (`backend/src/lib/exchangeRate.ts`).
- Código em `frontend/src/lib/shipping/` (funções puras testadas, hook `useShippingController`) e `frontend/src/components/shipping/`.

### Enquadramento automático da peça (`autoFit`) — 2026-10-05
- Objetivo: nos cards do catálogo a peça aparece pequena (PNG sem fundo com grandes margens transparentes, ou foto de estúdio em que a peça ocupa pouco do quadro). `autoFit` recorta em volta da peça com folga de 12% do maior lado da caixa — **sem remover o fundo de fotos opacas, sem esticar e sem ampliar**. Não mexe em cor, então não tem relação com a pendência da Política de Qualidade do realce de cor.
- Função pura `autoFitSubject` em `backend/src/lib/autoFit.ts` (todos os limites são constantes nomeadas no topo do arquivo). Detecção: PNG/WebP com >5% de pixels transparentes → caixa dos pixels com alpha > 16, ignorando respingos (mínimo de pixels por linha/coluna); foto opaca → `rembg` só LOCALIZA a peça (máscara) e o recorte é aplicado na foto ORIGINAL (a versão sem fundo nunca é entregue). Resultado `{ buffer, contentType, action: "cropped"|"unchanged"|"skipped", reason?, before/after: {w,h,coverage} }`; mantém o formato (PNG com alpha; JPEG/WebP qualidade 90). Em PNG transparente a folga que passa da borda estende a tela com transparência; em foto opaca é limitada às bordas.
- Não recorta (e nunca lança erro): `already_fitted` (caixa > 70% da área), `too_small_after_crop` (maior lado do resultado < 500 px), `rembg_unavailable` (rembg fora do ar; timeout de 60 s e no máximo 1 nova tentativa), `subject_not_found`, `unsupported_format`.
- 11ª operação da lista fechada: `autoFit`, sem parâmetros. **Ordem do pipeline: `removeBackground` → `autoFit` → brilho/contraste → `enhance_color` por último** (regra e frases-gatilho "enquadra a peça", "centraliza a pedra", "aproxima a pedra", "tira o espaço em volta" no system prompt da Claude; a ordem é só do prompt/atalhos — o backend não reordena).
- Rotas: as mesmas do tratamento (foto salva: `/treatment/preview|confirm|discard` + `/undo`; foto staged: `POST /api/images/treatment-preview-raw`, sem estado, nada gravado). Quando só `autoFit` foi pedido e nada foi recortado, o preview responde `{ unclear: false, noChange: true, notice }` (sem gravar no R2 nem devolver imagem) com a razão em português (ex.: "A peça já ocupa bem o quadro — não há o que enquadrar."); quando recorta, a resposta traz `notice` com o ganho de cobertura. Contrato aditivo: campo `notice` opcional e variante `noChange`.
- Admin: botão "Enquadrar peça" ao lado de "Realçar cores", "Mais nitidez" e "Remover fundo" (dica: "Aproxima a peça e tira o espaço em volta, sem cortar a pedra"). Preview antes/depois, confirmar, descartar e desfazer iguais aos demais tratamentos.
- **Script em lote** `backend/src/scripts/autoFitExistingPhotos.ts` (`npm run autofit:photos -- ...` ou, em produção, `node dist/scripts/autoFitExistingPhotos.js ...`). **Padrão é SIMULAÇÃO** (tabela produto/tamanho/cobertura antes e depois/ação/razão; só grava com `--apply`). Opções: `--limit=N`, `--product=slug1,slug2`, `--local-preview=<pasta fora do repo>`, `--api=<url>`, `--revert=<chave do manifesto>`. Ordem determinística (slug, posição, id). Imprime host e nome do banco sem credenciais e aborta se faltar variável `R2_*`.
  - Recomendado antes de aplicar em produção: na máquina do desenvolvedor, com o `rembg` local rodando, `npm run autofit:photos -- --api=https://<backend-publico> --local-preview=$HOME/autofit-preview` — só faz GET na API pública e gera JPEGs "antes | depois" para conferir; não grava nada.
  - `--apply`, por foto: pula se a key já contém `/auto-fit/` (idempotente/retomável; essas puladas não gastam o `--limit`); baixa do R2; roda `autoFit`; se recortou, sobe um **NOVO objeto** `products/{productId}/auto-fit/{uuid}.{ext}`, grava o manifesto e só então atualiza `ProductImage.url/key`, guardando o estado anterior em `previousUrl/previousKey` e espelhando `previousColorEnhanced/previousColorEnhanceLevel` exatamente como o `/treatment/confirm` (o "Desfazer" do admin volta ao antes). Falha numa foto não interrompe as demais; relatório final com contagens (recortadas, inalteradas, puladas por razão, erros).
  - **⚠️ O lote cria novos objetos no R2 e NUNCA apaga os antigos** (nem o script tem operação de exclusão) — o bucket só cresce até uma limpeza manual futura; é o preço de a reversão ser sempre possível.
  - Manifesto: gravado no próprio R2 em `_backups/auto-fit-AAAAMMDD-HHMMSS.json` (atualizado a cada foto, ANTES de mexer no banco): `{ imageId, oldUrl, oldKey, oldPrevious*, newUrl, newKey }`. `--revert=<chave>` restaura `url`, `key` e `previous*` — é simulação até receber `--apply`, e pula (`changed_since`) fotos que o admin tratou de novo depois do lote.
  - Como `previousUrl/Key` guarda um único nível, o `--apply` sobrescreve um "desfazer" anterior daquela foto; o manifesto guarda o valor antigo (`oldPrevious*`) e o `--revert` o recupera.
- Testes: `backend/tests/autoFit.test.ts` (função pura), `autoFitRoutes.test.ts` (rotas salva/staged, Claude/R2/rembg mockados), `autoFitScript.test.ts` (script com banco/R2/rembg em memória), casos novos em `claude.test.ts`; frontend em `src/lib/treatmentRequest.test.ts`. **Não verificado em produção**: o `rembg` real e o R2 real não foram exercitados neste ambiente (só mocks e imagens sintéticas).

### Lista de produtos do admin — paginação numerada (2026-10-05)
- Causa do bug: `ProductList` pedia só a 1ª página (pageSize padrão 20 do backend, total ignorado) e a busca por nome filtrava só os itens já carregados. Agora: páginas numeradas (Anterior/Próxima, reticências, versão compacta < 640 px), "Mostrando X–Y de N produtos", itens por página 25/50/100 (padrão 50; máx. do backend 100), filtros de categoria, subcategoria e status.
- O estado da lista fica na URL (`page`, `pageSize`, `q`, `category`, `subcategory`, `status`; valores inválidos caem para um padrão seguro). Editar/Novo passam a query string em `location.state` e o formulário volta exatamente para ela (`backToListPath`). Lógica pura em `frontend/src/lib/pagination.ts` e `productListState.ts` (testadas).
- Backend: `GET /api/products` ganhou `q` (contém, sem diferenciar maiúsculas, em `name` e `sku`; máx. 100 caracteres; total/páginas refletem o filtro; sem `q` nada muda, o catálogo público não foi tocado). O `contains` do Prisma NÃO escapa `%` e `_` do LIKE — por isso `escapeLikePattern` (`utils/escapeLike.ts`) trata esses caracteres como texto literal.

### Formas virou categoria de nível 1 — migração de dados (2026-10-05)
- **Lista fixa de categorias (por slug, posição):** `pedras-brutas` 1, `pedras-polidas` 2, `big` 3, `formas` 4, `homedecor` 5, `acessorios` 6. Subcategorias: Pedras Brutas (4), Pedras Polidas (2), Big (Ametistas, Calcitas, Citrinos) = 9; Formas, Homedecor e Acessorios não têm subcategorias. O schema Prisma NÃO mudou (sem migration); produto numa categoria sem subcategorias grava `subcategoryId = null` (regra `resolveSubcategoryId`, igual a Homedecor/Acessorios).
- **⚠️ Produção migra SÓ pelo script, NUNCA rodando o seed.** O seed só faz upserts (não move produtos nem remove a subcategoria antiga; se ela ainda existir, só avisa). Script: `backend/src/scripts/promoteFormasToCategory.ts` — `npm run promote-formas` (SIMULAÇÃO: mostra o plano, cada produto a mover e a subcategoria a remover; não grava nada) e `npm run promote-formas -- --apply`; em produção, `node dist/scripts/promoteFormasToCategory.js [--apply]`. Tudo por slug (os ids diferem entre ambientes).
- `--apply`: grava o manifesto ANTES e depois faz TUDO em uma única transação (Serializable): cria a categoria se faltar, fixa as posições (valores explícitos, nunca incrementos), move os produtos (`categoryId` novo, `subcategoryId` null) e remove a subcategoria só se nenhum produto a referenciar (a FK `Product.subcategoryId` é `ON DELETE SET NULL`: apagar com produtos os deixaria órfãos em silêncio). Qualquer falha desfaz tudo. Idempotente: depois de migrado diz "nada a fazer"; em estado parcial completa só o que falta.
- **Manifesto** (produtos movidos com `categoryId`/`subcategoryId` anteriores, registro completo da subcategoria, posições anteriores): banco remoto → R2 em `_backups/promote-formas-AAAAMMDD-HHMMSS.json` (obrigatório: sem `R2_*` o script aborta antes de abrir o banco); localhost → `~/promote-formas-backups/` (fora do repositório). Se o manifesto falhar, nada é gravado no banco.
- **Reverter:** `npm run promote-formas -- --revert=<chave _backups/... ou caminho local>` (simulação) e, para valer, `... --revert=<...> --apply`. Recria a subcategoria com o MESMO id, devolve os produtos, remove a categoria Formas se ficar vazia e restaura as posições. Produtos criados depois na Formas NÃO são tocados (listados no aviso) e, enquanto existirem, a categoria e as posições atuais são mantidas.
- Menu do catálogo: a tradução vem do mapa `categoryNames` (por NOME, igual para categoria e subcategoria) — "Formas" → "Shapes" em inglês, sem mudança nos arquivos de idioma.
